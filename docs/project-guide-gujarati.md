# Twofold — આખો પ્રોજેક્ટ કેવી રીતે કામ કરે છે (ગુજરાતી માર્ગદર્શિકા)

આ ફાઇલ જજસ સમક્ષ બોલવા અને સવાલોના જવાબ આપવા માટે છે. દરેક ટીમ મેમ્બરની ભૂમિકા અલગથી સમજાવેલી છે, એવી રીતે કે નવો ડેવલપર પણ સમજી શકે.

**નોંધ:** આ માર્ગદર્શિકા પ્રોજેક્ટના **અંતિમ સ્વરૂપ** વિશે છે — એટલે કે બધું કામ પૂરું થયા પછી અને ડિપ્લોય થયા પછી એપ કેવી દેખાય છે અને કેવી રીતે ચાલે છે તે અહીં લખેલું છે.

---

## પ્રોજેક્ટની એક-લાઇનમાં ઓળખ

**Twofold** એ વિદ્યાર્થીઓ વચ્ચેની **skill-exchange (સ્કિલ બદલી)** વેબ એપ છે — તું જે જાણે છે તે બીજાને શીખવ, અને જે શીખવું હોય તે બીજા પાસથી શીખ. પૈસાની જરૂર નથી, સીધું શીખવાનું-શીખવાનું બદલી (barter) થાય છે. દરેક વપરાશકર્તા **પોતાના પાસવર્ડથી** રજિસ્ટર કરે છે અને લૉગિન કર્યા પછી જ આખી એપ વાપરે છે.

---

## આખું સિસ્ટમ એક નજરમાં (Beginner માટે)

કલ્પના કરો — આ એપ એક રેસ્ટોરન્ટ જેવું છે:

1. **ફ્રન્ટએન્ડ (React + TypeScript + Vite)** = રેસ્ટોરન્ટનું ડાઇનિંગ એરિયા — જ્યાં વપરાશકર્તા બેસે, મેનૂ જુએ, ઓર્ડર આપે.
2. **બેકએન્ડ API (Spring Boot — Java)** = કિચન — અહીં બધું ખરેખર બને છે (લૉગિન ચકાસવો, સેશન બનાવવો, મેચિંગ ગણવું, મેસેજ મોકલવો, રિવ્યુ ઉમેરવો).
3. **SQLite ડેટાબેસ (`backend/twofold.db`)** = રસોડાની ફ્રિજ — બધો ડેટા (વપરાશકર્તા, સ્કિલ, સેશન, ચેટ, રિવ્યુ, પાસવર્ડ-હેશ, સેશન-ટોકન) અહીં સચવાય છે. ડેટાબેસ એક જ ફાઇલ છે, તેથી બેકઅપ લેવું એટલે જ એક ફાઇલ કૉપિ કરવી.
4. **સુરક્ષા-ગાર્ડ (Authentication)** = દરવાજા પરનો ગાર્ડ — દરેક વિનંતી પહેલાં ચકાસે છે કે વપરાશકર્તા સાચી ઓળખ સાથે લૉગિન કરેલો છે કે નહીં. વગર લૉગિને કોઈ લખી-વાંચી શકતું નથી.

**ડેટાની મુસાફરી આ રીતે થાય છે:**

```
વપરાશકર્તા UI પર બટન દબાવે
        ↓
React પેજ fetch વડે APIને પૂછે (જેમ કે POST /api/sessions)
        ↓
API પહેલાં સેશન-કૂકી ચકાસે — લૉગિન નથી તો 401, બીજાની ઓળખ વાપરે તો 403
        ↓
પછી ડેટા validation — ખોટું ડેટા હોય તો 400 (ચોક્કસ ભૂલ-સંદેશ સાથે)
        ↓
SQLite ડેટાબેસમાં લખાય / વાંચવામાં આવે
        ↓
API આખો નવો ડેટા-સ્નેપશોટ (Database object) પાછો મોકલે
        ↓
React સ્નેપશોટ જોઈને સ્ક્રીન ફરી દેખાડે
```

**ડેવલપમેન્ટમાં બે પ્રોસેસ, પણ વપરાશકર્તાને એક જ સાઇટ દેખાય:** `node scripts/dev.mjs` એક કમાન્ડથી બે વસ્તુ ચલાવે — API (Spring Boot, પોર્ટ 8080) અને UI (Vite, પોર્ટ 5173). Vite દરેક `/api` વિનંતીને આપોઆપ API તરફ મોકલે (proxy), તેથી બ્રાઉઝર માટે બંને **એક જ origin** છે — CORS ની કોઈ ગૂંચવણ નહીં. ડિપ્લોયમેન્ટમાં પણ UI અને API એક જ domain પર હોય છે, એટલે કૂકીઓ સહેલાઈથી કામ કરે.

**સ્નેપશોટ + પોલિંગ શું છે:** સર્વર પાસે આખા ડેટાનો એક મોટો object (version સાથે) છે. દરેક લખાણ (write) પછી version વધે છે. લૉગિન કરેલા બ્રાઉઝરનો ટેબ દર 1 સેકન્ડે ચેક કરે છે — જો version બદલાયો હોય તો જ સ્ક્રીન ફરી બનાવે, નહીંતર નહીં. આથી બે ટેબ વચ્ચે ડેટા તરત દેખાય છે અને idle ટેબ પર કોઈ ભાર નથી.

## ઓળખ અને સુરક્ષા (Authentication) — આપણી સૌથી મજબૂત બાજુ

એપ **પહેલાંથી જ સંપૂર્ણ લૉગિન-પાછળ બંધ** છે — ડેમો માટે પણ, ડિપ્લોય કરેલી સાઇટ પર પણ. એક જ વર્તન, ક્યાંય ખાસ કરેલું નહીં.

- **રજિસ્ટ્રેશન:** નામ, કેમ્પસ ઇમેઇલ, ઓછામાં ઓછા 8 અક્ષરનો પાસવર્ડ → `POST /api/auth/register`. પાસવર્ડ **BCrypt** વડે હેશ બનીને જ સચવાય — ક્યારેય સાદા અક્ષરમાં, ન ડેટાબેસમાં, ન લૉગમાં.
- **લૉગિન:** ઇમેઇલ અથવા handle + પાસવર્ડ → `POST /api/auth/login`. ખોટો પાસવર્ડ હોય કે અજાણી ઇમેઇલ — **એક જ સંદેશ** "invalid email or password", એટલે કે કોઈની ઇમેઇલ અસ્તિત્વમાં છે કે નહીં તે બહારથી ખબર ન પડે.
- **સેશન:** સફળ લૉગિન પર 256-બિટ અચૂક ટોકન બને છે અને **HttpOnly કૂકી** તરીકે બ્રાઉઝરમાં જાય છે. JavaScript તેને વાંચી શકતું નથી (એટલે XSSથી ચોરી શકાય નહીં), `SameSite=Lax` હોવાથી બીજી સાઇટથી POST કરીને કૂકી ચડાવી શકાય નહીં (CSRF અટકે). સેશન 7 દિવસનો છે અને વપરાશ ચાલુ હોય ત્યાં સુધી આપોઆપ લંબાય છે.
- **દરેક વિનંતી પર ચકાસણી:** કૂકી વગરની લખાણ-વિનંતી → **401**. પોતાને બદલે બીજાની ઓળખ વાપરવાનો પ્રયાસ (જેમ કે બીજાનું પ્રોફાઇલ એડિટ કરવું) → **403**. આ ચકાસણી **લખાણ થતાં પહેલાં** થાય છે — એટલે નિષ્ફળ પ્રયાસથી ડેટામાં કંઈ બદલાતું નથી.
- **સાર્વજનિક vs બંધ:** લેન્ડિંગ પેજ, `/auth` પેજ, નાનું `GET /api/stats` (માત્ર ગણતરીઓ — કેટલા વિદ્યાર્થી, કેટલી સ્કિલ) અને રજિસ્ટ્રેશન/લૉગિન — આ બધું વગર લૉગિને. **બાકીનું બધું** (`/api/state`, મેચેસ, પ્રીમિયમ, તમામ લખાણ, ડેશબોર્ડ સહિતના બધા પેજ) સેશન વગર નથી મળતું. વપરાશકર્તાનો ઇમેઇલ કે અન્ય વ્યક્તિગત માહિતી ક્યારેય લૉગિન-વગરના પ્રતિભાવમાં જતી નથી.
- **કોઈ ડિફોલ્ટ પાસવર્ડ નહીં:** સીડેડ (પહેલેથી ભરેલા) 12 વિદ્યાર્થીઓ **ડેટા માત્ર** છે — એમની પાસે પાસવર્ડ નથી, એમના ખાતાંમાં કોઈ લૉગિન કરી શકતું નથી. કોઈપણ વપરાશકર્તા 30 સેકન્ડમાં પોતાનું ખાતું બનાવે છે. આમ, ડિપ્લોય કરેલી સાઇટ પર **કોઈ શેર-કરેલો પાસવર્ડ અથવા ડિફોલ્ટ ખાતું અસ્તિત્વમાં નથી**.

## ડેટા (જે જજસને દેખાડશો)

એપ સાથે પહેલેથી ભરેલો ડેટા આવે છે: **12 વિદ્યાર્થીઓના પ્રોફાઇલ, 41 સ્કિલ (8 કેટેગરી), 12 સેશન, 14 રિવ્યુ, 9 મેસેજ**. આથી નવું ખાતું ખોલતાં જ Discover, Matches, ચેટ-ઇતિહાસ જેવા પેજ **તરત ભરેલા** દેખાય — ખાલી સ્ક્રીન નહીં. આ 12 પ્રોફાઇલ ડેટા તરીકે વપરાય છે (મેચિંગ, રિવ્યુ, સેશનનો ઇતિહાસ) — એમના ખાતાંમાં લૉગિન થતું નથી. ડેટા બગડે તો ડેવલપર-સ્તરે `POST /api/reset` (ડિપ્લોયમેન્ટમાં બંધ) અથવા `npm run db:reset` વડે આખો ડેટાબેસ પાછો શરૂઆતમાં આવે છે — UIમાં આ માટે કોઈ બટન નથી.

# ભૂમિકા 1 — ટીમ લીડ અને ફુલ-સ્ટેક ઇન્ટિગ્રેશન
### Patel Mann Sanjay — આર્કિટેક્ચર, API ↔ ફ્રન્ટએન્ડ જોડાણ, પ્રોજેક્ટ ડોક્સ

**મારી ભૂમિકા શું હતી:**
મેં આખા પ્રોજેક્ટની "દુકાન" ઊભી કરી — એટલે કે કયા ફાઇલ ક્યાં રહેશે, ફ્રન્ટએન્ડ અને બેકએન્ડ કેવી રીતે વાત કરશે, અને બધાનું એકસાથે કામ કરતું થાય તેની જવાબદારી. હું ટીમના દરેક સભ્યના ભાગને એકબીજા સાથે જોડતો (integrate કરતો) હતો.

**મેં શું બનાવ્યું:**
- Vite + React + TypeScriptનું પાયાનું સેટઅપ, `vite.config.ts` — જેમાં `/api` proxy ગોઠવ્યું જેથી UI અને API એક જ origin પર દેખાય (કોઈ CORS નહીં)
- `src/context/AppContext.tsx` — જે આખા એપમાં ડેટા-સ્નેપશોટ, સેશન-ચકાસણી અને 1 સેકન્ડનું પોલિંગ સંચાલિત કરે છે
- API અને ફ્રન્ટએન્ડ વચ્ચેનો ડેટા-માર્ગ: `src/data/api.ts` (UI માટે એક જ જગ્યાએથી વાંચવું-લખવું) અને `src/data/store.ts` (સ્નેપશોટ-બસ)
- બેકએન્ડનો મુખ્ય ભાગ: ડોમેન મોડેલ, `JdbcStorage` (SQLite સ્ટોરેજ), `ApiController`ના તમામ `/api` રૂટ, auth રૂટ (register/login/logout/me) અને `@Scheduled` રિમાઇન્ડર જોબ
- `docs/API.md`, `docs/DATA_MODEL.md` અને README — પ્રોજેક્ટના દસ્તાવેજો
- ડેટાબેસ-સ્તરનું માઇગ્રેશન: JSON-ફાઇલ-સ્ટોરથી **SQLite** પર જવું — schema ફાઇલો (`V1__domain.sql`, `V2__auth.sql`) વડે, જેથી નવું ડેટાબેસ હંમેશા સાચી રચનાથી બને

**એકદમ સરળ ભાષામાં:**
કલ્પના કરો કે એપ એક ઘર છે. મારું કામ હતું જમીન, દીવાલો અને વીજળીનું કામ — એટલે કે **પાયો**. બીજા ટીમ મેમ્બરોએ રસોડું (બેકએન્ડ), બેડરૂમ (ફ્રન્ટએન્ડ UI), ગાર્ડન (મેચિંગ એલ્ગોરિધમ) અને સિક્યુરિટી (ટેસ્ટિંગ) બનાવ્યા. હું એ બધાને એવી રીતે જોડ્યો કે ઘર ખરેખર રહેવા લાયક બને.

**બોલવા માટે (30 સેકન્ડ):**

# ભૂમિકા 3 — મેચિંગ એન્જિન અને શેડ્યુલિંગ

- દરેક શક્ય જોડીને **100 પોઇન્ટ**નો સ્કોર આપતું સ્કોરિંગ એલ્ગોરિધમ

**એકદમ સરળ ભાષામાં:**

**કેલેન્ડર શું છે:** `.ics` એ એક આંતરરાષ્ટ્રીય ફાઇલ-પ્રકાર છે — જેમ VHS ટેપ દરેક પ્લેયરમાં ચાલે, એમ `.ics` દરેક કેલેન્ડર એપમાં ચાલે. વપરાશકર્તા ફાઇલ ડાઉનલોડ કરે, ડબલ-ક્લિક કરે — સેશન એના કેલેન્ડરમાં સમય સાથે ઉમેરાઈ જાય.

# ભૂમિકા 4 — ચેટ, ટેસ્ટિંગ અને QA
### Gohel Devang Prakashbhai — cross-tab ચેટ સિંક, 82-ચેક ઓટોમેટેડ સ્મોક સ્યુટ, ટેસ્ટિંગ ડોક્સ

**મારી ભૂમિકા શું હતી:**
બે ભાગ: (1) બે વિદ્યાર્થીઓ વચ્ચેની **ચેટ**, અને (2) **આખી એપ તૂટે છે કે નહીં** તેની ચકાસણી. હું એ વ્યક્તિ હતો જે બીજાના કામમાં ભૂલ શોધતો, જેથી જજસ સામે એપ ક્યારેય શરમજનક રીતે ન તૂટે.

**મેં શું બનાવ્યું:**
- `src/pages/Chat.tsx` — મેસેજિંગ UI અને વાર્તાલાપ-સૂચી
- **Cross-tab સિંક** — એક ટેબમાં મેસેજ મોકલો, બીજા ટેબમાં 1 સેકન્ડમાં દેખાય
- **read receipts** — `message_reads` ટેબલ: કોને મેસેજ વાંચ્યું તેનો "seen" હિસાબ, વાંચેલા મેસેજ પછી ફરી "unread" ન બને
- `scripts/api-smoke.mjs` — **82 ઓટોમેટેડ ચેક** એક કમાન્ડથી ચાલે (લૉગિન, સેશન-ચક્ર, રિવ્યુ, ચેટ, 401/403/400/404/402 — બધા રસ્તા)
- `scripts/load-harness.mjs` — એકસાથે ઘણા વાચક-લેખક ચલાવીને પ્રતિસાદ-સમય માપવો (p95 ≈ 149 ms) અને ડેટા સાચો છે કે નહીં તે ચકાસવું
- **85 બેકએન્ડ ટેસ્ટ** (JUnit + MockMvc, 9 સ્યુટ) — દરેક રૂટ, ભૂલ-રસ્તા, auth-ચકાસણી અને કન્કરન્સી-વર્તન આવરી લે છે; JaCoCo આવરણ ~92%
- ટેસ્ટ-લાયક સુવિધા: `POST /api/reset` — ડેટા પાછો શરૂઆતમાં લાવે, પણ આ **ડિપ્લોયમેન્ટમાં બંધ** રહે છે (config દ્વારા) — સામાન્ય વપરાશકર્તા માટે અદૃશ્ય
- `docs/testing/` — TEST_SUMMARY, API_CONTRACT, DEFECT_LOG: શું ચકાસ્યું, શું ભૂલ મળી, શું સુધાર્યું — બધું લખેલું

**ચેટ કેવી રીતે કામ કરે છે (નવા ડેવલપર માટે):**
વપરાશકર્તા મેસેજ લખે → `POST /api/messages` → સર્વર પહેલાં ચકાસે કે તમે ખરેખર જેના નામે મોકલો છો તે જ છો (નહીં તો 403) → મેસેજ ડેટાબેસમાં લખે અને પાછો આખો સ્નેપશોટ મોકલે → UI બદલાવ બતાવે. બીજો ટેબ 1 સેકન્ડે ચેક કરે કે version બદલાયો? હા → નવો સ્નેપશોટ લે → મેસેજ દેખાય. કોઈ ખાસ સર્વર-પુશ નથી — નાના, સરળ અને ભરોસાપાત્ર.

**ટેસ્ટ સ્યુટ શું ચકાસે છે:**
એક જ કમાન્ડ (`node scripts/api-smoke.mjs`) ખરેખરના HTTP વપરાશની પૂરી જીંદગી ચલાવે છે: લૉગિન → સેશન રિક્વેસ્ટ (2 slots સાથે) → accept → complete → રિવ્યુ લખો → બીજો રિવ્યુ એ જ સેશન પર (અટકવું જોઈએ) → મેસેજ મોકલો → read-receipt → પ્રોફાઇલ એડિટ → ખોટા ડેટા મોકલો (400) → વગર લૉગિને લખવાનો પ્રયાસ (401) → બીજાની ઓળખ વાપરવાનો પ્રયાસ (403) → અજાણ્યું endpoint (404) → reset. અને છેલ્લે **82 માંથી 82 પાસ**.

**એકદમ સરળ ભાષામાં:**
ટેસ્ટ એટલે એપને રસ્તા પર ગાડી ચલાવીને ચકાસવી — સ્ટીયરિંગ કામ કરે છે? બ્રેક કામ કરે છે? હૉર્ન વાગે છે? મારી સ્ક્રિપ્ટ આ બધું આપોઆપ કરે છે અને છેલ્લે "82/82 પાસ" કે "FAIL" કહે છે. દરેક નવી સુવિધા પછી આ એક કમાન્ડ ચલાવો — જૂનું કંઈ તૂટ્યું હોય તો તરત ખબર પડે.

**બોલવા માટે (30 સેકન્ડ):**

## સામૂહિક ભાગ — ટીમ તરીકે અમે કેવી રીતે કામ કર્યું

દરેક વ્યક્તિની "પ્રાથમિક જવાબદારી" હતી, પણ દરેક ફીચર **બે લોકો મળીને** બનાવતા અને એકબીજાના કોડને ચેક (review) કરતા. આથી જજ પૂછે "તમે X જાણો છો?" તો દરેક સભ્ય આખા પ્રોજેક્ટની વાત કરી શકે છે, માત્ર પોતાના ભાગને ઊંડાણથી.

**ટેક્સ્ટ-સ્ટેક સંક્ષિપ્તમાં (બધા માટે યાદ રાખવું):**
Frontend: React 18 + TypeScript + Vite (Landing, Auth, Dashboard, Discover, Matches, Sessions, Messages, Profile, Pro) · Backend: Spring Boot (Java) REST API, પોર્ટ 8080 · DB: SQLite (`backend/twofold.db`, schema-માઇગ્રેશન ફાઇલો) · Auth: BCrypt + HttpOnly સેશન-કૂકી · Tests: 85 JUnit + 82 smoke + 24 parity + load p95 149 ms · Docs: README, API.md, DATA_MODEL.md, docs/testing/*

**ડેમોનો સૌથી સારો ક્રમ (5-7 મિનિટ):**
1. **Landing (વગર લૉગિને)** → `twofold.` બ્રાન્ડ, હેડલાઇન અને સાઇટની ગણતરીઓ (કેટલા વિદ્યાર્થી/સ્કિલ)
2. **Create profile** → 30 સેકન્ડમાં પોતાનું ખાતું — અહીંથી જ સિક્યુરિટી સમજાવો: પાસવર્ડ BCryptથી સચવાય, કૂકી HttpOnly છે
3. **Discover feed** → ઉપરના કાર્ડ પરનો સ્કોર બતાવો ("આ 92 કેમ મળ્યા?" — અહીં Aadityaનું 45/35/12/8 સ્કોરિંગ સમજાવો)
4. **Request session** → બે slots પસંદ કરીને મોકલવું (બીજી વ્યક્તિને)
5. **Accept (બીજા ખાતામાંથી)** → સેશન કન્ફર્મ + `.ics` ડાઉનલોડ બતાવવું
6. **Chat →** બીજું ખાતું incognito/બીજા બ્રાઉઝરમાં ખોલીને લાઇવ sync + read-receipt બતાવવું (Devangનો ભાગ)
7. **Review** → સેશન પર રેટિંગ+કોમેન્ટ, અને બતાવો કે એ પ્રોફાઇલ પર અને મેચ-સ્કોર (Trust) પર કેવી રીતે અસર કરે છે

(નોંધ: સીડેડ 12 વિદ્યાર્થીઓના પ્રોફાઇલ ડેટા તરીકે ભરેલા છે — ડિસ્કવર/મેચેસ તરત ભરેલા દેખાય. ઇન્ટરેક્ટિવ ફ્લો (સેશન, ચેટ, રિવ્યુ) બે ખરેખરના ખાતાં વચ્ચે ચલાવવો — ટીમ પાસે પોતાનાં બે ટેસ્ટ-ખાતાં હોય, અથવા ડેમોમાં જ બે ખાતાં ખોલવાં. કોઈ શેર-પાસવર્ડ નથી.)

**બધા માટે સામાન્ય સવાલો:**

- **પ્ર: સૌથી મુશ્કેલ શું હતું?**
  જ: એકસાથે અને સંતુલિત બદલી કરાવવી — એટલે કે મેચિંગ એલ્ગોરિધમના વજન એવા રાખવા કે કોઈને ફાયદો કે નુકસાન ન થાય; અને પછી તે જ ડેટાને બેકએન્ડ, UI અને ટેસ્ટમાં એકસરખું રાખવું. ઉપરાંત એપને ખરેખરની ઓળખ-સુરક્ષા (login, 401/403) આપવી અને એ બધું 85+82 ટેસ્ટમાંથી પાસ કરાવવું.

- **પ્ર: શું આ રિયલ વર્લ્ડમાં કામ કરશે?**
  જ: હા — REST API + SQLite ડેટાબેસ છે, એટલે API અલગ સર્વર પર અને ડેટાબેસ Postgres જેવામાં લઈ જવાય. **હમણાં જ અમે ખરેખરનું login (BCrypt + સેશન-કૂકી) ઉમેર્યું છે** અને આખી એપ તેની પાછળ બંધ છે — એટલે ડિપ્લોયમેન્ટ માટે તૈયાર. આગળના પગલાં: HTTPS, નોટિફિકેશન અને કેમ્પસ-વેરિફિકેશન.

- **પ્ર: તમે એકલા કર્યું કે ટીમે?**
  જ: ટીમે મળીને — દરેકની પ્રાથમિક જવાબદારી હતી, પણ દરેક ફીચર જોડે-જોડે બનાવવામાં આવ્યું અને એકબીજાના કોડનું review થયું.

- **પ્ર: ડિપ્લોય કર્યા પછી કોઈ ડિફોલ્ટ/ડેમો પાસવર્ડ તો નથી ને? (સુરક્ષાનો સવાલ)**
  જ: ના — આ જાણી-જોઈને આપણી પસંદગી છે. સીડેડ 12 વિદ્યાર્થીઓ પાસે પાસવર્ડ જ નથી, કોઈ ડિફોલ્ટ ખાતું નથી, કોઈ UIમાંથી બતાવેલો ડેમો-પાસવર્ડ નથી. દરેક વપરાશકર્તા પોતાના પાસવર્ડથી રજિસ્ટર કરે છે, પાસવર્ડ ફક્ત BCrypt-હેશ તરીકે સચવાય છે, અને દરેક લખાણ સર્વર-પર ચકાસાય છે (401/403). ડેટા-રીસેટ એન્ડપોઇન્ટ પણ ડિપ્લોયમેન્ટમાં બંધ છે.

- **પ્ર: શું તમે AI વાપર્યું?**
  જ: (આ સવાલનો ટીમ સાથે પહેલેથી સંમત થઈને જવાબ આપજો — ઉદાહરણ: "અમે ટૂલ્સનો ઉપયોગ સમજણ માટે કર્યો, પણ આર્કિટેક્ચર, એલ્ગોરિધમ અને દરેક નિર્ણય અમારા હતા, અને દરેક લાઇન સમજીને જ રાખી.")
